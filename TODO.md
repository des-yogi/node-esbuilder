## 1. Deploy на GitHub Pages

**Приоритет:** низкий (по необходимости)

Добавить возможность деплоя содержимого `build/` на GH Pages.

**Варианты реализации (выбрать один):**

- **А) GitHub Actions** — файл `.github/workflows/deploy.yml`, автоматический
  деплой при пуше в master.
- **Б) npm-скрипт** — `npm run deploy`, ручной деплой через `gh-pages` пакет.

**Критерии готовности:**
- Содержимое `build/` публикуется на `https://<user>.github.io/<repo>/`
- Не влияет на основную сборку

## 2. Линтинг: интеграция в сборку

**Приоритет:** средний

В `projectConfig.json` уже есть поля `"lintCss": true` и `"lintJs": false`,
но они пока ни на что не влияют.

**Что нужно:**
- При `npm run build` (production) — если `lintCss: true`, запускать
  `stylelint` перед компиляцией стилей. При ошибках — предупреждение в лог
  (не блокировать сборку).
- При `npm run build` — если `lintJs: true`, запускать `eslint` перед сборкой
  скриптов. При ошибках — предупреждение в лог.
- В dev-режиме — **не запускать** (чтобы не замедлять).
- Отдельные команды `npm run lint:css` и `npm run lint:js` уже есть —
  оставить как есть.

**Критерии готовности:**
- Линтинг управляется из `projectConfig.json`
- Не ломает сборку при ошибках линтинга (warn, не throw)
- Не замедляет dev-режим

## 4. Дебаунс (debounce) для вотчеров в dev-server

**Приоритет:** низкий

Сейчас при быстром сохранении нескольких файлов подряд (Ctrl+S → Ctrl+S)
каждое изменение запускает пересборку. Первое блокирует следующие через
`isRebuilding`, но последующие изменения просто **теряются**.

**Что нужно:**
- Добавить debounce (200–300 мс): при серии изменений запускать пересборку
  один раз после паузы
- Или: после завершения текущей пересборки проверять, были ли изменения
  во время неё, и если да — запустить ещё одну
