Техническое задание
на разработку многофункционального сборщика проектов на основе Node + esbuild и т.п. иснтументов

## 1. Введение
- Краткое описание целей сборщика:
Сборка фронтенда для разработчика в среде Windows 11 (поддержка самых современных (от v22+) версий node.js посредством NVM for Windows) без использования каких-либо js-фреймворков (React, Vue...) на основе "классического" (многостраничные сайты, не SPA) подхода к созданию сайтов и разделения отвественности: 
1. html -> Структура сайта, 
2. css -> Стилизация, 
3. vanilla js (стандарт ES2023) -> расширенный функционал. 
Принципы и философия построения: graceful degradation и progressive enhancement, а также mobile first и адаптивный дизайн. На выходе сборщика мы должны получать или dev-версию (без минификации и некоторых иных функций доп. обработки), или production-версию (готовую для имплементации, например в CMS). Для production-версии мы должны получить собранные html страницы очищенные от лишних комментариев и артефактов сборки (минификация html  - опционально с доп. параметров запуска сборщика), единый минифицированный стилевой файл (style.min.css), а также единый минифицированный js файл (script.min.js).  Также должны быть доступны опциональные возможности по линтингу css & js. В процессе работы (dev-режим) используется Live Reload при любых изменениях в коде и сохранении для визуализации изменений.
- Требования к поддерживаемым технологиям ( SCSS (Dart Sass), PostCSS, ES  & СommonJS, БЭМ, обработка изображений и т.д.):
Должны поддерживаться все современные технологии и тенденции в этой отрасли на данный момент и с возможностью расширения функционала и добавлению нового по мере необходимости (модульная система построения сборщика?) с приоритетом скорости работы (сборки бандла). Технологии, уже используемые мной на данный момент: препроцессинг SASS в версии SCSS (библиотека dart-sass), на проектах используется именование классов, файлов и переменных по БЭМ. Также очень важно иметь возможность использовать сторонние скрипты (библиотеки, плагины...), которые созданы с применением разных технологий модульности (ES & CommonJS). Сборщик должен поддерживать "горячее" создание новых блоков со всей минимальной дефолтной структурой и контентом, а также взятие этих новых блоков в обработку (отслеживание изменений, реакция на эти изменения, live reload и т.п.)!
- Краткое сравнение с предыдущей gulp-сборкой (мотивация замены):
Предыдущая галп сборка вполне удовлетворяет своим функционалом, однако многие составные части (npm-пакеты), как и сам gulp 4 перестают поддерживать современные версии node.js (с современными подходами и функционалом) из-за чего невозможна или очень затруднена модернизация. Поэтому текущая задача - создать новую версию сборщика с похожими возможностями или даже шире, но без таких ограничений на данный момент и в будущем. Поэтому принято решение создать новый быстрый, современный, легко расширяемый инструмент для сборки с широкими возможностями по конфигурации.

## 2. Функциональные требования
Парадигма!
1. Используется именование классов, файлов и переменных по БЭМ.
Блоки - "block-name"
Элементы - "block-name__elem-name"
Модификаторы - "block-name__elem-name block-name__elem-name--mod"
2. Список использованных в проекте БЭМ-блоков и доп. файлов указан в ./projectConfig.json
3. Каждый БЭМ-блок в своей папке внутри ./src/blocks/ (стили, js, картинки, разметка; Обязателен только стилевой файл!).
4. Есть глобальные файлы (статика): стилевые, js, шрифты, картинки.
5. Диспетчер подключения стилей ./src/scss/style.scss генерируется автоматически (!) при старте любой задачи.
6. Для разметки можно использовать микрошаблонизацию при помощи аналога "gulp-file-include".
7. Перед созданием коммита запускается проверка стилевых файлов, входящих в коммит.
- Описание структуры исходников (src, blocks, assets, build и др.).

### 2.1. Архитектура проекта и структура директорий
Структура проекта:
build/          # Папка сборки, здесь работает сервер автообновлений.
src/            # Исходные файлы
      _include/     # - фрагменты html для вставки на страницы (page_head.html и page_bottom.html)
      blocks/       # - блоки проекта
      css/          # - можно положить добавочные css-файлы (нужно подключить в copiedCss, иначе игнорируются)
      fonts/        # - можно положить шрифты проекта (будут автоматически скопированы в папку сборки)
      img/          # - можно положить добавочные картинки (нужно подключить в addImages, иначе игнорируются)
      js/           # - можно положить добавочные js-файлы (нужно подключить в addJsBefore, addJsAfter или copiedJs, иначе игнорируются)
      scss/         # - стили (style.scss скомпилируется, прочие нужно подключить в addCssBefore, addCssAfter или singleCompiled, иначе они будут проигнорированы)
      index.html    # - главная страница проекта, на этом же уровне будут и другие страницы
- Особенности хранения блоков по БЭМ:
Смотреть выше в Парадигма. 
Вот образец структуры типичного БЭМ-блока на моих проектах:
Каждый блок лежит в ./src/blocks/ в своей папке. Каждый блок - как минимум, папка и одноимённый scss-файл.
Возможное (расширенное) содержимое блока:
demo-block/               # Папка блока
      img/                    # Изображения, используемые блоком и обрабатываемые автоматикой сборки
      some-folder/            # Какая-то сторонняя папка, не обрабатываемая автоматикой
      demo-block.scss         # Стилевой файл блока
      demo-block--mod.scss    # Отдельный стилевой файл БЭМ-модификатора блока
      demo-block.js           # js-файл блока
      demo-block--mod.js      # js-файл для отдельного БЭМ-модификатора блока
      demo-block.html         # Варианты разметки (как документация блока или как вставляемый микрошаблонизатором фрагмент)
      readme.md               # Какое-то пояснение. Должен собираться всегда (если не пустой) после основного "родительского" стилевого файла.
Обязательным из всех файлов является только "demo-block.scss", всех остальных может и не быть!
Минимальное (дефолтное) содержимое блока, создаваемое генератором новых блоков (на данный момент это отдельный скрипт, запускаемый вручную из консоли командой node createBlock.js имя-блока [доп. параметр]):
demo-block/               # Папка блока
	img/  
      bg-img/  
      demo-block.scss
      demo-block.html
      readme.md
Эта структура формируется скриптом createBlock.js, который лежит в корне проекта. Если это можно сделать как-то более интегрировано и более удобно, готов рассмотреть предложения.
- Гибкость настройки путей и шаблонов.
Структура проекта приведена выше и на данный момент изменять ее не предполагается, хотя предусмотреть возможность ее модификации было бы неплохо. При в верстке я привык использовать мини-шаблонизатор, который помогает поддерживать БЭМ структуру, аналогом которого для среды Vite является "vite-file-include".

### 2.2. Сборка и обработка стилей
- Поддержка SCSS (SASS) с автогенерацией style.scss.
- Включение служебных и пользовательских файлов SCSS.
- Использование PostCSS (autoprefixer, mqpacker (или аналог в более современном варианте) и др.).
- Поддержка опционального разделения CSS по media queries.
- Поддержка singleCompiled для отдельных файлов.
- Подключение переменных и миксинов во все SCSS-блоки.
- Минификация и генерация sourcemaps.
Файл-диспетчер подключений (.src/scss/style.scss) формируется автоматически при страте сборщика на основании указанных в ./projectConfig.json блоков и доп. файлов.
Также есть глобальные стили, как собственно и js, например, являющиеся содержимым сторонних библиотек, которые должно просто копироваться (без обработки) и подключаться ДО или ПОСЛЕ собранного бандла. 

### 2.3. Сборка и обработка JavaScript
- Обработка файлов блоков и глобальных файлов.
- Гибридная поддержка ES modules и CommonJS, настройка alias.
- Конкатенация, минификация, sourcemaps.
- Возможность копирования отдельных JS-файлов (библиотек).

### 2.4. Сборка HTML
- Поддержка инклюдов (vite-file-include и базовых шаблонов).
- Очистка сервисных комментариев.
- Генерация итоговых HTML-файлов для build.

### 2.5. Работа с изображениями
- Копирование и оптимизация изображений (jpeg, png, gif, svg, webp).
- Генерацию webp-версий (aviff - опционально) можно производить не рядом с исходниками, а уже в папке со сборкой "build/img" для того, чтобы можно было сразу же вставлять эти файлы в html (отдельные блоки и страницы).
- Генерация SVG-спрайтов, его минификация и вставка отдельных символов инлайново в html (отдельные блоки и страницы) или в виде base64 для фоновых изображений (postcss-inline-svg).
- Логирование и обработка ошибок.

### 2.6. Работа с другими ассетами
- Копирование шрифтов (ttf, woff, woff2, eot, svg).
- Копирование изображений (jpg, webp, png, gif, svg) из корневой папки img или аналогичной папки в составе отдельного бэм-блока. При этом все изображения должны проходить обработку, описанную в предыдущем пункте (2.5. Работа с изображениями)
- Копирование видеофайлов (mp4, webm, ogg). Проводится без обработки.
- Возможность копирования дополнительных CSS/JS. Опционально. Проводится без обработки

### 2.7. Dev-сервер и автоматизация
- Запуск dev-сервера с горячей перезагрузкой (BrowserSync или аналог).
- Желательна поддержка https и выбора порта
- Вотчеры для всех типов файлов и блоков (SCSS, JS, HTML, изображения, конфиг).
- Автоматическая пересборка при изменениях.
- Кастомные уведомления об ошибках и событиях (желательно предусмотреть цветовую индикацию, например красный - для крит. ошибок, желтый - предупреждения, зеленый - информация про успешное завершение).

## 3. Нефункциональные требования

### 3.1. Кроссплатформенность
- Работа под Windows 11 (Node.js >= 20 через NVM for Windows), желательно, но не обязательно под macOS и Linux.

### 3.2. Документируемость и поддержка
- Описание команды для запуска и сборки.
- Документация по структуре конфигов и расширяемости.

### 3.3. Производительность
- Быстрая инкрементальная сборка.
- Минимизация времени на rebuild.

### 3.4. Безопасность и качество кода
- ESLint/Stylelint.
- Проверка на ошибки сборки.

## 4. Конфигурируемость и расширяемость

- Поддержка projectConfig.json.
- Гибкая настройка списков подключаемых файлов (before/after, singleCompiled и др.).
- Возможность легко добавлять новые блоки, миксины, плагины PostCSS и т.д.

## 5. Перечень опциональных и продвинутых функций

- Вынос CSS по media queries (extractMediaQuery). Можно организовать эту функцию отдельной командой, типа "npm run build -extractMedia"
- Поддержка кастомных плагинов.
- Генерация документации по блокам.

## 6. Этапы реализации и требования к результату

- План-график (этапы, приоритеты).
На первом этапе надо реализовать базовый функционал сборщика. Сборку html, css, js из папки src в папку build с правильной структурой.
На втором этапе - сборка и (или) копирование ассетов, обработка изображений
- Состав итоговых артефактов (исходный код, документация, базовые шаблоны).

## 7. Приложения

- Примеры структуры проекта.
Базовую структуру проекта смотреть выше.
Базовая структура итоговой папки со сборкой:
build/
	img/ (все изображения проекта)
	video/ (все видео проекта, если есть)
	js/ (основной js бандл "script.min.js" + отдельно подключаемые lib.js, например: swiper.min.js, bootstrap.bundle.min.js и т.п., если есть)
	css/ (основной бандл "style.min.css" со стилями проекта + отдельно подключаемые lib.сss, если есть)
	fonts/ (все шрифты проекта, если есть)
	index.html (главная страницы проекта)
	about.html (страница проекта)
	other-page.html (страница проекта)
- Примеры конфигов.
- Примеры команд CLI.
Стандартные и привычные для меня команды:
"npm start" (запуск dev сервера разработки)
"npm run build" (сборка production версии)
"npm run lint:js" (проверка js)
"npm run lint:css" (проверка стилей)
